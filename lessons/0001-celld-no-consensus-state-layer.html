0. 开场：我们解剖的是一台什么机器

celld 是 Deno 官方（denoland）2025-04 开源的一个 Rust 守护进程，一次把两个问题叠在一起回答：

  • 能不能在自有机器上跑 Cloudflare Workers + Durable Objects？ —— 每个 node 内嵌 V8，执行 Wrangler bundle，API 兼容 Workers。
  • 能不能不做共识，就做出「分布式 + 持久化」？ —— 节点之间没有 membership protocol、没有 failure detector、没有 consensus service。

它用对象存储（S3/R2/GCS/Azure Blob）当整个系统的「控制平面 + 长期记忆」。每个业务对象是一个 cell：一个命名服务器 + 一个私有 SQLite 数据库。cell 空闲时在 bucket 里只是一个对象，成本几乎为零——官方数字：8GB 节点装 1000 个常驻 cell，每个 cell 约 $0.05/月。

这堂课的双重读法：表面读法是理解 celld 的「条件写所有权 → epoch fencing → RPO=0」协议链；深层读法是理解一个反直觉的分布式设计命题——什么情况下你可以不要 Paxos/Raft？这对你评估自家 Database/Agent 平台的架构取舍有直接迁移价值。

1. 概念地图：cell / node / fleet / bucket

概念是什么类比
cell一个 Durable Object：命名 + 私有 SQLite 库，单线程一致一个「用户 / 文档 / 聊天室 / AI agent」
node一个 celld 进程（一台机器），内嵌 V8，跑 Worker一个可替换的计算单元
fleet共享同一 bucket 的所有节点；一 fleet 跑一个应用一个「部署集群」
bucket你拥有的对象存储：部署产物 + cell 状态 + 所有权/租约记录系统的「真相磁盘」+ 「选举裁判」

关键设计决定：没有任何「服务发现/控制面」服务。节点之间怎么互相找到？通过 bucket 里的 leases。节点如何知道一个 cell 归谁？bucket 里的 ownership record。初看起来违背直觉——对象存储的读写延迟不是很高吗？——但注意：路由请求是热点路径，但所有权记录是低频路径（每次激活/迁移才写一次）。把「热数据」与「仲裁元数据」分开，是这套设计的第一个杠杆。

2. 支柱① 所有权 = 条件写（conditional write）

一个 cell 同一时刻只能被一个节点拥有，否则两台机器写同一个 SQLite 库 → 数据损坏。
传统解法：Raft/Paxos 选一个 leader。celld 的解法：让对象存储当裁判——它对 bucket 提三个要求：

  1. 条件 create：对象已存在时写入必须失败
  2. 条件 overwrite：对象在我读后被改过，写入必须失败（CAS）
  3. 读后写一致性：写成功后读回的一定是那份

获取 cell：无记录 → create；有记录 → compare-and-swap。bucket 只接受一个赢家，于是两个节点不可能同时 acquire 同一个 cell——仲裁被交给一个已经为「原子性」付过钱的外部服务。代价：存储必须真的实现这些条件（所以 B2/Hetzner/DO Spaces 被排除，celld 在这些存储上「不正确」），并且启动时要跑 storage test 验证。

“A node claims a cell by writing a small record to the bucket… Object storage therefore decides who wins.”

这里有个对产品人的启示：把「权威」委托给云存储的条件写，等于把「成员管理」整个功能外包——你不再需要实现心跳超时、phantom leader 检测、leader 选举日志。系统更小，故障面更小。

3. 支柱② 数据 fencing = epoch 前缀

有了「谁拥有」还不够，还要防「曾经拥有者继续写」。celld 引入 fencing epoch：每次激活（包括 takeover 和本地 wake）都把 epoch +1。复制到 bucket 的数据写在 cells/<cell>/ltx/e<epoch>/ 前缀下——epoch 在对象 key 里。

  • 失去所有权的节点可以继续写，但只能写进已被取代的前缀
  • restore 时选择最新的、含 LTX 数据的 epoch 前缀
  • 每个 epoch 只有一个 writer —— fence 通过「写哪」来保证，而不是「禁止写」

这是经典 fencing token 思想（Martin Kleppmann 写过）的存储化实现：不阻止旧主写，只保证旧主的写永远不可见。用前缀隔离而不是锁，好处是失败节点不需要任何「同步配合」——它被切成什么样都行，迟到的写自然落到过期前缀。

4. 支柱③ RPO=0：承认的写必须真的活着

celld 对用户承诺：告诉你说成功的写，绝不会丢（recovery point zero）。怎么证明一次写跨故障存活？两条路径：

4.1 单节点（bucket proof）

  1. capture committed SQLite write 为 LTX 数据
  2. 上传到 bucket —— 一个存储往返
  3. 读一次 ownership record：如果我仍然是这个 node @ 这个 epoch，才确认

那个「读 ownership」是关键：分区节点可能本地 commit + 复制进过期前缀，但 ownership 读会显示新主人，于是它不会确认。它用「读权威记录」而不是「比时钟」，所以暂停的进程、乱了的时钟都骗不过它。

4.2 两节点以上（fleet proof，默认）

  1. owner 把每次写发给 1-2 个 follower（ensemble）
  2. follower 必须 fsync 才应答
  3. 应答 = 写已跨故障存活（两个磁盘）—— 比 bucket 往返快一个量级
  4. 之后再把数据补传 bucket（长期记忆），bucket 上传可稍后完成

数据表：region-local bucket 一轮写约 90 ms；实验室跨区域约 600 ms；有第二个节点后约 25 ms。

为什么 2 节点是分水岭：node 从「其他节点」里挑 follower，不会把自己算进去 → 至少 2 个节点才能完成 fleet proof。默认 CELLD_DURABILITY=fleet，所以单节点集群也会请求 fleet 姿势——得不到就退回 bucket proof，正确但慢，README 直接说「write latency matters → 跑 ≥2 nodes」。

fleet proof 的安全性还依赖一个细节：takeover 会封（seal）前一个 node-log session——新主人恢复前先把旧 session 封死，于是旧 owner 不能再完成新的 fleet proof。这解释了为什么「条件 node-log record + 冷激活 recovery gate」存在。

5. 冷激活恢复门（takeover recovery gate）

冷激活读 bucket 前，先检查前主人的 log records：

前主人记录状态含义动作
absent该 session 从未确认过任何「fleet 持久」写直接 restore
sealed恢复已完成直接 restore
open / recovering可能丢了已确认但未上传的尾部跑 recovery：CAS 封记录 → 封可达 follower → 上传它们保留的 segments/bundles → 标记 sealed，然后才能 restore

一句话：不能跳过恢复就开始读，否则已确认的数据可能还躺在别的节点磁盘上。restore 本身读「从事务 0 开始的完整连续链」（读取最新 epoch 前缀里带的全部 LTX），所以被 fence 的非确认尾部可能会被读出来——这不违反契约：「没确认」不等于「必须没有」，多读出来的是未确认写，会暴露但不是丢失。

6. 自围栏（self-fencing）与运维契约

每个节点持一条 bucket lease（默认 TTL 10s，过了 1/3 就续期）。

  • 续不上 → 等到已发布过期时间过了 → self-fence：停所有 active cell、fail 所有未完成请求、exit code 3
  • lease 被别的 writer 替换/删除 → 立即 fence（权威已经移走）
  • fence 不写 bucket —— 每个 peer 已经看到 lease 死/被替换，他们通过 ownership records 拿 cell
  • 请求路由时每次都对比「当前时间 vs 已发布过期时间」—— fence 跑之前请求也已经安全
运维契约（部署者必须知道）：celld 必须跑在 supervisor（systemd/Docker restart policy/K8s）下；fenced 进程立即退出，没有 supervisor 重启 = fleet 容量缺失。supervisor 重启间隔 ≥ 一个 lease 生命周期，且不设尝试上限。fence 是终结态，重启走冷激活路径——「节点失败」是一等输入，不是恢复流程。

7. LTX：SQLite 复制的血脉

复制的载体不是 binlog 而是 LTX——SQLite 的 WAL 事务格式。celld-ltx crate 是 2026-08-03 从 rustyriver（Litestream v0.5 的 Rust 重实现）快照过来的，直接承接 Litestream（Ben Johnson）+ superfly/ltx 的格式血统：

  • 普通 L0 writer 发旧 frame 表示；v0.5.2 encoder/compactor 发新 block 表示；两者文件版本都是 3
  • 默认开启节点级 L1 compaction（additive 对象），takeover 读「几十个对象」而不是「几千个」
  • 混合舰队需 CELLD_LTX_COMPACTION=0 直到所有节点能读 block 文件（reader-first 升级）
  • 有意思的取舍：Litestream 的 leaser（对象存储租约）被 port 后 删除了——celld 用 conditional-write record + epoch 前缀 fencing，再加一层 lease file 反而打架

专业点：SQLite 的 WAL 天然是 append-only 日志——这就是「捕获天然复制源」的好处：不用解析 SQL、不用改 SQLite 内核，读 WAL 即成 LTX。

8. 与主流分布式数据库的三个对比

8.1 vs OceanBase（Paxos 多副本）

OB 用 Paxos 组内同步多副本，靠 clog 复制，多数派确认；celld 是单写者 + 外部仲裁——写入只在一个 node 发生，仲裁交给对象存储的原子条件写。OB 追求「任何副本可读、故障毫秒级自动切换」的通用性；celld 用「一 cell 一主、切换要经过 bucket 恢复」换来了没有成员协议、没有选主协议的系统简化。适用性分界：你的数据能不能按「命名实体」天然分片？能 → celld 模式划算；不能（跨片事务密集、需要强一致多副本直读）→ Paxos/Raft 不可省。

8.2 vs MongoDB Atlas（分片 + 副本集）

Mongo 的 shard = 副本集 + config server + mongos 路由；celld 的 cell 分片 = bucket 里的对象 + 节点按流量领取。Mongo 是「数据库提供分片」；celld 是「运行时提供分片」（cell 即分片，应用从第一天就按实体划分）。共同点：都意识到「共享同一数据库的争用」可以通过分区消除。

8.3 vs Litestream（单机复制工具）

Litestream 是把单个 SQLite 库持续复制到对象存储（恢复点在秒级）；celld 把它升维成「每个 cell 自己的 SQLite + 复制 + 所有权」，并加上了多节点快速确认（fleet proof）和自动 takeover。血缘：celld 复用 LTX 格式，所以理论上 Litestream/celld 可互读 LTX 文件（v0.5.16 reader 兼容）。

9. 产品与成本结构视角

维度celld 的选择产品含义
空闲成本inactive cell = bucket 对象，近零「大量用户/agent 挂着但不活跃」不再是成本灾难——按事件付费思维
扩容加一台机器、起一个 node、共享 bucket无 join 服务、无账号服务；但也不 rebalance 现有 cell
多租户一 fleet = 一应用；无多租户调度alpha 边界清晰：先解决单租户跑通，多租户留给产品层
TLS/网络不终结 TLS，peer 明文+HMAC，需私有网络安全模型简单但依赖部署纪律

对 kejun 的产品启发（RISE 模型语境）：celld 展示了「把控制面压进一个你本来就拥有的存储」的产品化路径——用户不需要学一套新 API，只需要一个 bucket + 一个二进制。对 AI Agent 场景：每个 agent 一个 cell（记忆+调度+收件箱在私有 SQLite）正是 OBCloud/DBaaS 可以考虑的「按 agent 计费」运行时模型。

11. 下课动作 + 下一步方向

今天先做一件事：本地 30 秒跑起来，看 cell 状态机。

curl -fsSL https://celld.dev/install.sh | sh
celld dev

（或 docker run --rm ghcr.io/denoland/celld --version；celld dev 不需要 Docker/云桶，自动起 local object store，Worker 听 http://127.0.0.1:9876。）

然后选下一步方向（回复 A / B / C / D）：

  • A. 跑起来 + 拉代码读：写一个带 Durable Object + SQLite 的小 Worker，celld deploy 到本地 bucket，观察 cell 从 inactive → resident → idle 的状态迁移。
  • B. 源码深潜（node_log / ltx_repl）：进 crates/celld/node_log.rs（212K）与 ltx_repl.rs（143K），把「fleet proof 确认 + takeover 封 session」在代码行数上钉死。
  • C. 单写者复制家族横向对比：celld ↔ Litestream ↔ Turso/libSQL ↔ rqlite 的「无共识/弱共识」设计谱系，提炼可迁移手法。
  • D. 部署到真实 bucket：R2/MinIO + 2 节点，跑 storage test 与 kill-test，验证 guarantees 承诺。
