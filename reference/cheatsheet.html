celld 速查表

denoland/celld · Self-hosted, distributed Durable Objects · 一页可打印

0. 一句话

celld = 把 Cloudflare Durable Objects 搬到自己机器上的 Rust 守护进程。每个「cell」= 一个命名服务器 + 一个私有 SQLite 库。所有权用对象存储条件写仲裁，不用共识协议。

1. 词汇表

词含义
cell一个 Durable Object：命名 + 私有 SQLite 库，单线程一致性，可休眠
node一个 celld 进程（一台机器），内嵌 V8，跑 Wrangler bundle
fleet共享同一 bucket 的所有节点；一 fleet 跑一个 application
bucket你拥有的对象存储（S3/R2/GCS/Azure），存部署 + cell 状态 + 所有权记录
LTXSQLite 复制事务格式（Litestream → rustyriver → celld-ltx）
epoch每次激活递增的 fencing 代数；复制写入 e<epoch>/ 前缀下
ensemblecell 主人的 1-2 个 follower 节点；fleet proof 的仲裁集合
RPO=0承认的写必然已跨故障存活（recovery point zero）
self-fence节点失去 lease 后自我终止（exit 3），不写 bucket，直接退出

2. 三条设计支柱

支柱机制解决的问题
① 所有权 = 条件写create/CAS 一个 ownership record；bucket 只接受一个赢家「谁拥有 cell」——不需要成员协议/故障检测/共识
② 数据 fencing = epoch 前缀复制写入 cells/<cell>/ltx/e<epoch>/，restore 选当前 lineage陈旧的写不能污染新主人的状态
③ RPO=0 = 双重证明bucket proof（单节点）或 fleet proof（2+ 节点，follower fsync）「写成功」必须真的跨故障存活

3. bucket 必须提供的三性质 + storage test

  1. 条件 create（对象存在则失败）
  2. 条件 overwrite（对象被改后 CAS 失败）
  3. 读后写一致性（写完立即可读回）
已认证：S3 / R2 / Tigris / GCS / Azure Blob（Release tests 跑 R2）。
不可用：Backblaze B2、Hetzner Object Storage、DO Spaces（无条件写）→ celld 在此类存储上不正确（两节点可同时拥有一个 cell）。
MinIO community：条件写可用、能过 storage test，但未认证生产（一个已知坏版本 2025-09-06，用 09-07 之后）。

celld diagnose 发 4 个条件写验证（2 个应失败）：「ok bucket conditional write (create, reject-create, update, reject-stale)」，失败即退出。

4. 写路径（两种持久化证明）

单节点（bucket proof）2+ 节点（fleet proof，默认）
顺序写 WAL → 上传 bucket → 读 ownership 确认写 WAL → 发给 1-2 follower → follower fsync → 应答 → 之后补传 bucket
延迟~90ms（region-local）/ ~600ms（跨区域）~25ms（有第二节点后）
确认规则上传后读 ownership record，仍是我这个 node@epoch 才确认follower fsync 即认为持久；takeover 会封旧 node-log session

5. 生命周期与压力控制

  • cell 状态：resident(active/idle) → hibernated（保留 WebSocket）→ inactive（仅 bucket 里的对象，近零成本）
  • 冷激活：check 前主人 node-log records（absent=从未确认过 / sealed=恢复完成 / open→先 recovery 再 restore）
  • 节点 lease：bucket 里一条记录，1/3 生命周期续期（TTL 默认 10s）；续不上→ self-fence → exit 3 → supervisor 重启
  • 超载：单 cell 最多 64 并发 fetch（CELLD_MAX_CELL_REQUESTS），超载 503 + Retry-After: 1
  • 内存：CELLD_MAX_RSS_MB（默认 80% 阈值，95% 绝对上限）、CELLD_V8_HEAP_LIMIT_MB（默认 128MB ≈ 5 万 WebSocket 客户端）

6. 常用命令

celld dev                          # 本地开发，worker 在 :9876，状态在 .celld/dev
celld deploy . --bucket s3://...   # 部署（需要 esbuild on PATH）
celld --bucket s3://... --listen :8080 --internal-listen :8081 --advertise ...   # 起节点
celld diagnose --bucket ...        # 诊断 + storage test + peer probe
celld cell list --bucket ...       # 列出 DO 实例（Class:ID，1000/请求）
celld d1 migrations apply ledger   # D1 迁移
celld kv bulk put sessions export.json   # KV 导入（wrangler 格式）
celld queue pause/resume jobs      # 队列控制

7. 关键环境变量

变量作用
CELLD_DURABILITY (fleet|bucket)持久化证明方式；默认 fleet
CELLD_OUTPUT_GATE (0|1)关闭复制等待 = 接受已确认写丢失；默认 1
CELLD_TTL_MS节点 lease 生命周期，默认 10000
CELLD_LTX_COMPACTION (0|1)L1 压缩对象；混合舰队旧 reader 需 0
CELLD_MAX_RESIDENT_CELLS每节点常驻 cell 硬上限
CELLD_MAX_RSS_MB / CELLD_V8_HEAP_LIMIT_MB内存压测阈值 / isolate 堆上限
CELLD_ACTIVATIONS并发冷激活上限（默认 CPU 数或 128）
CELLD_ADDR / CELLD_INTERNAL_ADDR / CELLD_ADVERTISE三个监听/通告地址（公网/内网分开）
CELLD_DEPLOY_POLL_S / CELLD_DEPLOY_MAX_AGE_S部署轮询 30s / 代码强制下线 60s

8. 限制（alpha 诚实面）

  • 一 fleet 只有一个 application；无多租户/账务/托管 ingress
  • 节点加入不 rebalance —— 流量分配 unowned/released cell
  • 不终结 TLS；peer HTTP 明文→ 必须私有网络 / WireGuard / Tailscale
  • peer 通道靠 fleet HMAC（绑定 body + 时钟限制 + 重放保护）
  • Windows 不支持；仅 Linux x86-64 / ARM64 / Apple Silicon
  • celld 对 B2/Hetzner/DO Spaces 直接不正确（不能 fence）
